# Private registration draft journal and structural preflight

The journal is the first implementation step of the Owner-approved [external registration route](../../docs/architecture/assessments/BKL-049-External-Origin-Registration-Plan.md). It preserves private submission drafts only. Separate read-only configuration and catalog-context checkers are described below. None is an operational catalog, acceptance service, F4 snapshot producer or publisher. There is no command-line entry point and no directory discovery of scientific images.

`build_draft` takes explicitly selected UTF-8 JSON bytes and their independently selected expected digest. It preserves original bytes, including missing values, in an envelope fixed to DRAFT_NOT_ACCEPTED / PRIVATE_NOT_APPROVED / scientificAuthority NONE. Any source claim of acceptance remains untrusted source content; it never changes the envelope. Duplicate JSON keys, nonfinite numbers and malformed input reject. Limits: 256 KiB source, 512 KiB revision, 32 levels / 32,768 JSON values, 128 revisions per submission and 1,024 directory entries scanned.

`retain_draft` appends a create-only revision to a pre-existing private directory. The caller supplies the expected current head, null only for a new empty submission chain. Each revision links to the previous digest; all prior revisions and nondecreasing receipt timestamps are verified before append. These are registration receipt times, never substituted for acquisition or configuration validity. Filenames are derived from the submission ID, not scientific names or source paths. A changed revision conflicts. An exact retry supplies the retained current digest and returns DUPLICATE_NOOP. A lost acknowledgement requires read-only reconciliation against independent trusted evidence, not blind retry with a fabricated anchor.

`load_chain` verifies every retained revision against the externally retained current digest. Missing revisions, changed bytes, unknown files in the selected namespace, stale expected heads and reparse paths reject. An independently refreshed anchor is required: replaying an obsolete anchor together with a rolled-back directory cannot be detected by an offline library. Returned hashes establish integrity, not operator authentication or scientific acceptance.

The module reuses only canonical encoding/hash and filesystem primitives from the existing private archive utility. It does not invoke PixInsight parsing or consume its evidence as authority. Hard-link create-if-absent is the atomic commit primitive; unsupported filesystems fail closed. No overwrite fallback, catalog write, network, image payload read, cloud action, backup scheduling or cleanup operation is provided. The caller controls directory privacy/ACLs, storage access and anchor retention. Hostile concurrent filesystem administration and directory-metadata power-loss durability remain outside the assurance claim.

## Verification and operation boundary

Synthetic tests cover exact source preservation, embedded false acceptance claims, integrity, duplicate keys, malformed/oversized/deep input, invalid IDs/revisions, conflicting append, corruption, missing/rolled-back revisions, timestamp order, failed atomic commit, restore with an external anchor and symlink rejection. The existing archive/delivery suites verify reused filesystem primitives. Linux/Windows CI runs the new suite. Local Windows symlink tests may skip where privileges are unavailable; report those skips explicitly.

A private pilot dry run may retain the existing incomplete candidate and restore that draft to a separate private scratch directory. This proves draft retention only; it does not prove production backups, accept the candidate or establish a real image/workflow binding. Draft bytes and receipts stay outside Git and the public preview bucket.

Still required for the full registry: governed scientific validation and acceptance rubric, explicit record decisions, complete mandatory context, operational retention/restore acceptance, current eligible snapshot export with collision/revision/withdrawal/quarantine checks, and unchanged F4 handoff. None is implied by a successful draft append. No new approval for implementation already authorized by PR #462 is needed; actual record acceptance remains separate.

Rollback removes the draft API from use and reverts its additive code/test/CI change. Preserve private draft files and independent receipts; this tool does not delete or migrate them.

## Configuration structural preflight

`configuration_preflight.check_configuration(source, expected_digest)` checks an explicitly selected private JSON object containing `observatory`, `telescope`, `camera` and `configuration`. It reuses the journal's bounded exact-byte JSON parser; no filesystem, network, clock, image read or registration operation is called. The input is an internal selection, not an AP-013/AP-014 schema replacement. A report retains the selected source digest privately and emits only fixed section/field/code diagnostics, never source values or unknown keys.

The checked subset is DSDM-002 sections 2.2 and 5.1/5.2/5.3/5.5: mandatory presence and basic types, explicit UTC calendar syntax, chronological audit/configuration intervals, positive versions/optical quantities and exact selected observatory/telescope/camera references. Optional nulls remain unknown. Unknown fields are findings, not silently ignored. Instrument-configuration status uses the documented DRAFT/ACTIVE/RETIRED vocabulary; other equipment/lifecycle vocabularies, identifier allocation, timezone interpretation and provenance require governed review and are not claimed verified. The selected references are not resolved against a live registry.

`NO_STRUCTURAL_FINDINGS` means only that this bounded subset found no errors. Every report keeps `acceptanceEligible=false`, DRAFT_NOT_ACCEPTED, PRIVATE_NOT_APPROVED and scientificAuthority NONE. Even a syntactically valid `validFromUtc` does not prove historical validity or association with an acquisition. No date, equipment, priority, UTC interpretation or quality default is generated. This module cannot accept records, export an F4 snapshot or replace the full metadata validator and acceptance rubric.

Eleven synthetic cases exercise missing configuration despite known models, missing historical time, invalid/naive/offset times, fractional-time ordering, exact-reference mismatch, unknown optional values, malformed types, source integrity/resource bounds, fixed private diagnostics and no acceptance on structurally clean input. CI runs these on Windows and Linux. Rollback reverts this additive checker and its parser extraction, leaving all private drafts intact.

## Catalog context validator

`catalog_context.check_catalog_context(source, expected_digest)` checks selected candidate metadata without writing a record or invoking a generator. Its private input kind is `DSG_PRIVATE_CATALOG_CONTEXT_CANDIDATE_V1`, with `configurationSelection` in the preceding checker's format and six arrays: `projects`, `campaigns`, `targets`, `observations`, `sessions`, `catalogItems`. Each array contains 1..8 selected records. The digest authenticates bytes only: source authority, source-digest meaning and currentness require independent governance. The nested configuration digest is derived from the selected input, not presented as an independent authority anchor.

The field matrix follows AP14-W02 sections 2.3, 3, 4.1–4.5 and 4.12. Required version/source/audit fields and selected entity fields are checked without defaults. Checks include dates/calendar/UTC order, integer priority 1..5, positive record versions, bounded names, coordinates, numeric integration maps, explicit identifier patterns, exact foreign keys, duplicate IDs and target names, duplicate catalog entity/version pairs, and selected configuration/site references. Duplicate identities are removed from lookup eligibility rather than resolved by last writer. If session UTC instants are supplied, instants outside the selected configuration interval are findings; day-only evidence is not converted to midnight or UTC. Timestamp syntax accepts explicit `Z` and at most six fractional digits.

This internal profile accepts SHA-256 source-digest syntax and session-only catalog items. IDs are not minted or derived from names; session and configuration references use a bounded generic identifier syntax because namespace allocation/mapping remains an external gate. Selection-scoped uniqueness is not global registry uniqueness. Canonical target names are compared case-insensitively; alias disambiguation remains part of governed identity review. Supersession references must resolve within the selection and cannot self-reference. This is not a revision ledger or a current-snapshot exporter. Complex completion criteria and external catalog-reference payloads are explicitly unsupported when supplied; null remains permissible.

AP14-W01 supplies the implemented catalog project/session/quality/mode/reconciliation/state vocabularies; DSDM-002 supplies target types. AP14-W02 names but does not enumerate project type, campaign status, observation status and completion state. Values in these fields receive `VOCABULARY_UNRESOLVED`, as does a supplied transfer state whose mapping is not established in this profile. Missing fields remain REQUIRED. No vocabulary is borrowed silently from a different entity model. All reports distinguish `findings` from `vocabularyGaps` and retain the full non-acceptance envelope even when structural findings are empty.

Eighteen synthetic tests cover every mandatory field, duplicate/colliding identities, unresolved chains, malformed enum/types, timezone/date non-inference, ordered intervals, unsupported details, forged acceptance, resource limits and diagnostic privacy. Windows/Linux CI runs them with existing archive, draft and configuration regressions. The complete [validation/acceptance boundary](../../docs/architecture/assessments/BKL-049-Private-Registry-Validation-and-Acceptance-Gates.md) identifies the remaining production gates. Revert this additive module/tests/CI/documentation to roll back; retain all private evidence. No public schema, generated catalog or existing API is replaced.

## Asset metadata and composed registration checks

`asset_metadata.check_asset_metadata(source, expected_digest, measurement_source=..., measurement_digest=...)` checks a private `DSG_PRIVATE_ASSET_SELECTION_V1` selection. It contains explicit `originalAssetId` / `previewAssetId` and 1..8 records in each of `assets`, `volumes`, `locators`, `integrityRecords`, `relations`. Each record follows the selected required/optional DSDM-002 section 7 fields plus section 2.2 audit fields. IDs remain caller-supplied; generic bounded syntax does not allocate a DSDM identity or settle namespace mapping. The checker opens no scientific file and follows no locator.

It checks required fields/types/enums, signed-64-bit nonnegative byte sizes, percentages, complete canonical hash/algorithm pairs, selected ID/reference uniqueness, volume logical names, locator-to-asset coherence, active-location collisions, integrity predecessor identity/time/cycles and explicit derivative direction. Relative paths are checked without opening or rewriting them: absolute paths, drive/ADS syntax, empty/dot/parent components and NUL reject. Only separators are normalized for collision comparison; filesystem case/alias semantics and actual availability remain unverified. Known SHA-256 hashes do not merge distinct asset identities.

The selected pair must have an explicit candidate relation whose source is the preview and target is the original, using `PUBLICATION_VARIANT_OF` or `DERIVED_FROM`. This is the internal pair-selection convention, not a reconstructed lineage fact. No filenames supply identity or association. Relation evidence remains unverified, and a nonnull processing-run reference is explicitly unsupported until that context is governed. Lifecycle, locator availability and relation confidence vocabularies remain unresolved rather than borrowing meanings from unrelated records.

Measurements are a separately selected `DSG_PRIVATE_ASSET_MEASUREMENTS_V1` object with 1..8 `items`; each has exactly `assetId`, `sha256`, `sizeBytes`, `scope`, `measuredAtUtc`, `evidenceRef`. Scope must be `FULL_FILE_BYTES`. Header-only hashes, absent/duplicate measurements, wrong selected IDs, sizes or hashes produce findings. Measurements have their own expected byte digest; callers must establish origin, actual full-file scope, independence and freshness. The API does not perform measurements or authenticate a scope claim. SHA-256 is a bounded comparison profile, not a new canonical hashing policy. Optional source timestamps, when selected, require explicit UTC syntax; no local timestamp is converted or discarded from the retained source.

Positive MATCH/COMPUTED integrity claims cannot contradict a supplied canonical asset hash. Recorded MISMATCH/FAILED/PARTIAL results and selected withdrawn/quarantined/violated/unreadable states appear in `eligibilityFindings`; the historical negative evidence is preserved. This is a report, not a state-transition engine, recovery or revocation service. All reports retain acceptanceEligible false regardless of structure or matching bytes. A successful comparison does not establish a current F4 snapshot.

`registration_validation.check_registration_metadata` composes the existing catalog/configuration and asset reports. Its private `DSG_PRIVATE_REGISTRATION_SELECTION_V1` input contains `catalogContext`, `assetSelection`, explicit `sessionId` and `targetId`. It checks an unambiguous session/catalog selection and the session's observation-to-target chain. Nested digests derive from the anchored parent selection; they are not independent authority anchors. Measurement bytes/digest remain separate inputs. The parent report retains all nested findings, vocabulary gaps, eligibility findings and non-acceptance limits. No acceptance, journal write, F4 invocation, snapshot export or publication operation exists.

Twenty-five synthetic tests cover mandatory omissions, selected and unselected duplicate identities, references, paths, integrity history, hash/size/full-file scope, negative eligibility, bounds/privacy and composed-context mismatch. Existing suites remain unchanged. Rollback reverts the additive modules/tests/CI/documentation, retaining every private original, draft and receipt. Real registration still requires the unresolved scientific/provenance/identity gates, distinct operator decisions, operational retention and the unchanged F4 guard.
