# Private registration draft journal

This is the first implementation step of the Owner-approved [external registration route](../../docs/architecture/assessments/BKL-049-External-Origin-Registration-Plan.md). It preserves private submission drafts only. It is **not** a scientific metadata validator, operational catalog, acceptance service, F4 snapshot producer or publisher. There is no command-line entry point and no directory discovery of scientific images.

`build_draft` takes explicitly selected UTF-8 JSON bytes and their independently selected expected digest. It preserves original bytes, including missing values, in an envelope fixed to DRAFT_NOT_ACCEPTED / PRIVATE_NOT_APPROVED / scientificAuthority NONE. Any source claim of acceptance remains untrusted source content; it never changes the envelope. Duplicate JSON keys, nonfinite numbers and malformed input reject. Limits: 256 KiB source, 512 KiB revision, 32 levels / 32,768 JSON values, 128 revisions per submission and 1,024 directory entries scanned.

`retain_draft` appends a create-only revision to a pre-existing private directory. The caller supplies the expected current head, null only for a new empty submission chain. Each revision links to the previous digest; all prior revisions and nondecreasing receipt timestamps are verified before append. These are registration receipt times, never substituted for acquisition or configuration validity. Filenames are derived from the submission ID, not scientific names or source paths. A changed revision conflicts. An exact retry supplies the retained current digest and returns DUPLICATE_NOOP. A lost acknowledgement requires read-only reconciliation against independent trusted evidence, not blind retry with a fabricated anchor.

`load_chain` verifies every retained revision against the externally retained current digest. Missing revisions, changed bytes, unknown files in the selected namespace, stale expected heads and reparse paths reject. An independently refreshed anchor is required: replaying an obsolete anchor together with a rolled-back directory cannot be detected by an offline library. Returned hashes establish integrity, not operator authentication or scientific acceptance.

The module reuses only canonical encoding/hash and filesystem primitives from the existing private archive utility. It does not invoke PixInsight parsing or consume its evidence as authority. Hard-link create-if-absent is the atomic commit primitive; unsupported filesystems fail closed. No overwrite fallback, catalog write, network, image payload read, cloud action, backup scheduling or cleanup operation is provided. The caller controls directory privacy/ACLs, storage access and anchor retention. Hostile concurrent filesystem administration and directory-metadata power-loss durability remain outside the assurance claim.

## Verification and operation boundary

Synthetic tests cover exact source preservation, embedded false acceptance claims, integrity, duplicate keys, malformed/oversized/deep input, invalid IDs/revisions, conflicting append, corruption, missing/rolled-back revisions, timestamp order, failed atomic commit, restore with an external anchor and symlink rejection. The existing archive/delivery suites verify reused filesystem primitives. Linux/Windows CI runs the new suite. Local Windows symlink tests may skip where privileges are unavailable; report those skips explicitly.

A private pilot dry run may retain the existing incomplete candidate and restore that draft to a separate private scratch directory. This proves draft retention only; it does not prove production backups, accept the candidate or establish a real image/workflow binding. Draft bytes and receipts stay outside Git and the public preview bucket.

Still required for the full registry: governed scientific validation and acceptance rubric, explicit record decisions, complete mandatory context, operational retention/restore acceptance, current eligible snapshot export with collision/revision/withdrawal/quarantine checks, and unchanged F4 handoff. None is implied by a successful draft append. No new approval for implementation already authorized by PR #462 is needed; actual record acceptance remains separate.

Rollback removes the draft API from use and reverts its additive code/test/CI change. Preserve private draft files and independent receipts; this tool does not delete or migrate them.
